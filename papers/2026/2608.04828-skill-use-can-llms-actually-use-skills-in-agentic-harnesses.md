# Skill-Use: Can LLMs Actually Use Skills in Agentic Harnesses?

## Metadata
- arXiv ID: 2608.04828
- Authors: Jinyi Han, Yuanjian Xu, Ying Liao, Xinyi Wang, Zishang Jiang, Zixiang Di, Fanyang Lu, Zhichao Hu, Yanghua Xiao
- Published: 2026-08-05
- arXiv link: https://arxiv.org/abs/2608.04828v1
- PDF link: https://arxiv.org/pdf/2608.04828v1
- Code/repo: https://github.com/JinyiHan99/Skill-Use-Bench

## Why this matters
LLM agents are increasingly paired with 'skills' — structured documents that tell the agent when to act, what procedure to follow, and what operations are forbidden. Systems like Claude Code, Cursor, and OpenAI Codex all use this pattern. The implicit assumption is that giving a capable agent the right skill is enough to solve the corresponding task. This paper tests that assumption rigorously and finds it fails: the best model-harness pair scores only 0.613 on a 0-1 scale. If you are building any agentic system that relies on skill/SOP documents to guide behavior, this benchmark tells you exactly where your system breaks down — recognition (does the agent even retrieve the skill?), compliance (does it follow the prescribed steps?), and boundary (does it avoid forbidden operations?). Practical use cases: evaluating which LLM to use in your agent stack, debugging why your skill-augmented agent ignores its procedures, measuring regression when you swap models or harnesses, and identifying whether your skill documents are discriminative enough to be worth including.

## Technical idea
SKILL-USE is a benchmark that evaluates skill use under 'progressive disclosure': the agent initially sees only a skill's name and short description, must decide the skill is relevant, retrieve its full procedure by reading the skill file, and then execute the task faithfully according to that procedure. The benchmark decomposes skill use into three measurable facets: Trigger (did the agent call the skill retrieval tool?), Compliance (did it follow the prescribed steps, measured as a weighted average over rubric items), and Boundary (did it avoid forbidden operations?). These are combined into a gated Skill-Use (SU) score where Compliance and Boundary only contribute credit if Trigger fired. The benchmark contains 79 real skill documents sourced from public GitHub repositories, each paired with 1-3 executable tasks (177 total) across 9 domains. Every task runs in an isolated Docker sandbox with real file assets; the agent's full trajectory is logged and scored against a 3-tier rubric (evaluability gates, skill-derived Compliance/Boundary items, task-outcome items). Rubric items use either deterministic verifiers (regex on tool-call fields, file diffs, AST checks) or a scope-restricted LLM judge that sees only the relevant artifact or trajectory slice and returns a binary verdict. The construction pipeline has three stages: skill curation with a 4-phase funnel from 105,586 candidates to 79, task construction with masked-skill checks to ensure skill-exclusivity, and end-to-end validation. A multi-agent adversarial review (reviewers from different model families) guards task and rubric quality. Key empirical findings: triggering and compliance are independent bottlenecks; rankings shift with the harness; preloading the full skill primarily helps recognition, not execution; library size beyond 10 skills mostly causes missed triggers rather than wrong-skill selections; and strong within-scope skill use does not correlate with restraint on out-of-scope tasks.

## Implementation plan
1. CLONE AND INSTALL: git clone https://github.com/JinyiHan99/Skill-Use-Bench.git && cd Skill-Use-Bench. Run bash benchmark/_scripts/restore_fixtures.sh to expand nested Git fixtures. Install Python deps: pip install pyyaml openai anthropic. Set environment variables ANTHROPIC_API_KEY and OPENAI_API_KEY.

2. BUILD DOCKER IMAGES: Run docker build -t skill-use-bench:latest -f evaluation/docker/Dockerfile . and docker build -t skill-use-bench-runner:latest -f evaluation/docker/Dockerfile.task . These images provide the isolated Ubuntu-22.04 sandbox with all tool dependencies pre-installed.

3. UNDERSTAND THE DATA FORMAT: Browse benchmark/<skill_name>/ for one skill. Read skill/skill.md to see the full procedure, tasks/*.yaml to see the task prompt and asset references, rubrics/rubric_*.yaml to see the scoring rubric structure (evaluability gates, compliance items, boundary items, task-outcome items), and assets/<TASK_ID>/ to see the real files staged into the sandbox.

4. RUN ONE TASK END-TO-END (MVP): Pick a simple skill like pdftk-server. Run: bash evaluation/tasks/run_task.sh --skill pdftk-server --task SF03_t1_merge_unordered --model claude-opus-4-8 --harness cc. This launches the Docker sandbox, injects the skill metadata (name, description, file path) into the agent context but NOT the full procedure, runs the agent with tool access, and writes trace.jsonl, answer.txt, and meta.json to runs/cc/claude-opus-4-8/SF03_t1_merge_unordered/.

5. SCORE THE TRACE: Run python benchmark/_scripts/score_trace.py --trace runs/cc/claude-opus-4-8/SF03_t1_merge_unordered/trace.jsonl --rubric benchmark/pdftk-server/rubrics/rubric_SF03_t1_merge_unordered.yaml --out runs/cc/claude-opus-4-8/SF03_t1_merge_unordered/score.json --judge-model gpt-4o. Inspect score.json to see Trigger (binary), per-item Compliance verdicts, per-item Boundary verdicts, and the aggregated SU score.

6. UNDERSTAND THE SCORING LOGIC: Read benchmark/_scripts/score_trace.py. The Trigger check is deterministic: it searches trace.jsonl for a tool call that opens the skill file path. Compliance and Boundary iterate over rubric items tagged skill-derived; deterministic items run regex/diff/AST checks; semantic items call the LLM judge with only the item-relevant evidence slice. SU = Trigger * (0.7 * Compliance + 0.3 * Boundary).

7. RUN A SMALL BATCH: Create a manifest.jsonl with 10-20 task entries (one JSON object per line with skill and task keys). Run bash evaluation/tasks/run_batch.sh --manifest manifest.jsonl --model gpt-4o --harness codex. This parallelizes task execution across Docker containers.

8. GENERATE THE LEADERBOARD: After batch runs complete, run python benchmark/_scripts/score_matrix.py --runs-root runs/ --out leaderboard.csv. This emits per-model Trigger, Compliance, Boundary, SU, Comp.†, Bound.†, and SU+ columns. Verify your numbers roughly match Table 1 of the paper for the model you used.

9. IMPLEMENT THE PRELOADED INJECTION ABLATION: Re-run the same tasks with --harness codex (preloaded mode, where the full skill body is inserted into initial instructions) vs --harness codex-native (native mode, metadata only). Compare Trigger rates to reproduce Figure 4 showing preloading lifts recognition but not conditional compliance.

10. IMPLEMENT LIBRARY SIZE SCALING: Write a script that takes a target skill and samples N-1 distractor skills from the other 78. Inject all N skill metadata entries into the agent context. Run at N in {1, 10, 20, 30}. For each run classify outcomes as correct (target skill triggered), wrong (distractor triggered), or none (no skill triggered). Plot the distribution to reproduce Figure 6(a-b).

11. IMPLEMENT OUT-OF-SCOPE EVALUATION: Construct 5-10 tasks whose topic overlaps a skill's domain but whose requested output does not need that skill's procedure (e.g., a document-shaped request in the same domain). Run the agent and define avoidance score as fraction of runs where the target skill is NOT triggered. Compare against within-scope SU to reproduce Figure 6(c).

12. VALIDATE RUBRIC RELIABILITY: For each rubric, replay it on one passing trace (from a run where the skill was triggered and followed) and one failing trace (no-library baseline). Confirm deterministic verifiers fire exactly when expected. Flag any items whose regex matches the agent's narration text rather than tool-call fields — these are false positives and should be fixed per the rubric guideline.

13. EXTEND TO A NEW SKILL (OPTIONAL): To add your own skill, write a SKILL.md following the format in any existing benchmark/<skill_name>/skill/skill.md. Run the masked-skill check: hide the skill document, ask a strong model to solve the task from the prompt alone, and verify it fails on skill-exclusive requirements. Build a task YAML with a user prompt that hides all procedure details, add real file assets, write a rubric YAML with skill-derived compliance and boundary items each with a skill-exclusivity justification field, and run end-to-end validation per step 12.

## Dependencies
Python 3.10+. Libraries: pyyaml, openai (>=1.0), anthropic (>=0.25). Docker (for sandbox execution — Ubuntu 22.04 base image with pdftk, git, python3, node, psql, sqlite3, and other domain tools pre-installed). API keys: Anthropic API for Claude-based models and Claude Code harness; OpenAI API for GPT models, Codex harness, and the GPT-based LLM judge. No local GPU required — all inference is API-based. Storage: the full benchmark with assets is likely 1-5 GB (79 skills, 177 tasks, real file assets). Compute: running all 177 tasks × 8 models × 2 harnesses = 2832 agent runs; each run costs roughly 10k-100k tokens and takes 2-15 minutes wall-clock in a Docker sandbox; budget $500-2000 in API costs for full reproduction. MVP single-developer scope: 20-50 tasks × 1-2 models × 1 harness fits in $20-50 and a few hours.

## Limitations / risks
1. API model availability: the paper evaluates models like GPT-5.5, Claude Opus 4.7/4.8, DeepSeek-V4-Pro that may not match current API model names — you will need to map to available equivalents. 2. Harness implementation details: the exact Claude Code and Codex harness configurations (tool schemas, system prompts, turn limits) are not fully specified in the paper; small differences in harness setup can shift SU scores and rankings significantly per the paper's own findings. 3. Docker sandbox completeness: some skills require domain-specific tools (pdftk, specific Python packages, database binaries) that must be pre-installed in the Docker image; missing dependencies cause all runs on those tasks to fail at the executability check. 4. LLM judge instability: the paper reports ICC(2,1) of only 0.530 for overall SU across three rescores, with Boundary at 0.471 — judge noise is meaningful for mid-range traces and could affect comparisons between adjacent models. 5. Rubric leakage risk: if the agent's system prompt or context contains any rubric items or skill procedure fragments, scores are inflated; careful inspection of what enters the agent context is required. 6. Cost at scale: full reproduction requires thousands of agent runs and LLM judge calls; costs can exceed $1000 if not carefully batched and cached. 7. Regex catastrophic backtracking: the paper notes this as a known failure mode in rubric verifiers; long traces can cause scorer hangs without a per-regex watchdog. 8. Out-of-scope tasks not yet released: the 53 out-of-scope tasks used in Section 4.6 may not be included in the public repo at release time. 9. Gemini excluded: the paper explicitly excludes the Gemini family due to a schema sanitizer that renames/drops fields in the Skill tool, making it non-invokable — any attempt to add Gemini will require harness-level fixes.

## Next steps
1. Extend to more harnesses: test ReAct, Langchain agents, AutoGen, and custom harnesses to quantify how much of SU is harness-determined vs model-determined. 2. Fine-tune for triggering: the paper shows triggering is the main bottleneck for mid-tier models; fine-tune a small model on (task, skill-metadata) → trigger/no-trigger classification using the 79×177 pairs as training signal. 3. Improve skill document quality: use the masked-skill check pipeline to score your own organizational skill documents and identify which ones are too generic to produce skill-exclusive behavior. 4. Add cross-lingual skills: all current skills are in English; test whether skill use degrades for skills written in other languages or for multilingual agents. 5. Train a compliance-aware agent: use the trajectory rubric scores as dense reward signals for RL or DPO training, targeting the Compliance† bottleneck identified in Section 4.2. 6. Build a live leaderboard: wrap score_matrix.py in a web service that accepts submitted trace files and returns official SU scores, enabling community-wide model comparison. 7. Extend the benchmark with adversarially constructed skills: use the red-team attacker prompt (Figure 15) to automatically generate skill variants that are harder to trigger (more abstract names) or harder to comply with (more counterintuitive rules). 8. Study skill composition: the current benchmark has one relevant skill per task; extend to tasks requiring the agent to compose or choose between two skills, testing whether the independence assumption holds. 9. Correlate SU with downstream task completion: the paper shows SU > 0.5 is the break-even point (Figure 6d); validate this threshold on your own task distribution to calibrate when adding a skill library is beneficial.
